# trellis-break-loop

当一个 Bug 修复了两次以上依然复发、或者“修好 A 坏了 B”陷入死循环时，**立刻停下手头的修补工作，执行深查**。

## 止血排查步骤

| 步骤 | 动作 | 产物 / 输出 | 要点 |
|------|------|-------------|------|
| 1. 立刻停手 | 停止继续尝试打局部补丁 | 无 | 别再盲猜修改，防止越改越乱 |
| 2. 编写必现用例 | 编写一个能稳定复现 Bug 的最小单测或脚本 | 失败的测试用例（红灯） | 无法稳定复现前，绝不动业务代码 |
| 3. 复盘前次修复 | 检查前两次修改到底改了哪、为什么没治本 | 记入 `analysis.md` | 常见漏网原因：时序异步、缓存未失效、分层找错、副作用未清理 |
| 4. 追踪完整数据流 | 从用户输入/触发点一步步 trace 到出错位置 | 根因结论 | 找到真正的污染源头，而不是在出错点草率加 `if (!x) return` |
| 5. 彻底修复与验证 | 修改根源问题，跑通单测 | 测试转为绿灯 | 确保原问题与历史单测全过 |

## 硬性卡点

1. **写不出复现用例/无明确复现步骤，坚决不改代码**。
2. **严禁在报错处简单套 try-catch 或加判空来掩盖问题**。
3. **彻底搞清原因后，先向用户说清楚根因与长效方案，再动手修改**。
