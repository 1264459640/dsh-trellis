# trellis-break-loop

当调试陷入反复拉锯时使用本技能——例如同一问题被修复了两次以上，或者某 Bug 在声称“已修好”后仍然不断复发、甚至修好 A 坏了 B 时，**立刻停下手头的修补工作，执行根本性深查**。

## 止血排查五步走

| 步骤 | 环节 | 具体操作 | 关键产出与要求 |
|---|---|---|---|
| 1. 立刻停手 | 止血 | 停止盲目尝试打局部补丁 | 别再凭猜想盲改代码，防止污染现场或引入次生问题 |
| 2. 编写必现用例 | 稳定复现 | 编写一个能稳定复现 Bug 的最小单测、脚本或精确步骤 | 失败的测试用例（红灯）；**无法稳定复现前，绝不动业务代码** |
| 3. 复盘前期尝试 | 失效分析 | 逐一审视之前的每一次修复尝试，记录于 `analysis.md` | 查明为何没能触及真因：时序异步、缓存未失效、分层找错、副作用未清理等 |
| 4. 追踪完整数据流 | 定位真因 | 从触发源头一步步追踪到失效点，阐明底层机制 | 找到真正的污染源头，而不是在出错点草率套 try-catch 或无脑加判空 |
| 5. 彻底修复与防复发 | 治本与验证 | 修改根源机制，跑通复现单测与既有全量测试 | 测试全部转绿；提炼防坑说明写入规范（Spec Note）杜绝未来重蹈覆辙 |

## 产物与沉淀

- 将复盘分析、失效机制与长效方案持久化记录到任务目录下的 `analysis.md` 或 `research/` 资料中。
- 在任务收尾时，通过 `trellis-update-spec` 将本次教训转化为工程规范，确保团队与 Agent 不再踩坑。

## 硬性卡点

1. **写不出复现用例/无明确复现步骤，坚决不改代码**。
2. **严禁在报错处简单套 try-catch 或加判空来掩盖问题**。
3. **彻底搞清真因后，先向用户说清根因与方案，再动手修改**。
4. **必须将结论沉淀到磁盘文件**：聊天上下文会被压缩截断，但磁盘产物不会丢失。
