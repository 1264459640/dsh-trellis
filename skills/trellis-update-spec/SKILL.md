# trellis-update-spec

在任务完工、准备提交代码前运行本技能。快速复盘本次开发是否产生了值得长期保留的经验或规矩。

## 复盘判断矩阵

| 判断维度 | 典型例子 | 记录位置 | 处理动作 |
|----------|----------|----------|----------|
| 1. 踩坑与易错点 | 某库的时区 Bug、隐蔽的异步时序问题 | `.trellis/spec/<package>/<layer>/` 或 `guides/` | 记录原因与正确写法，防止下次再踩 |
| 2. 新增统一约定 | 全局错误码规范、统一接口封装方式 | `.trellis/spec/<package>/<layer>/index.md` | 补充规矩条款与示例代码 |
| 3. 重大技术选型 | 决定用某种技术替代旧方案（ADR） | `.trellis/spec/decisions/` | 记录决策背景与权衡原因 |
| 4. 普通日常修改 | 无新坑、无新规矩、常规业务逻辑 | 汇报中说明“无需更新规范” | **不做多余改动，直接跳过** |

## 操作流程

1. **审视改动**：快速对照本次 git diff。
2. **决策与执行**：
   - 有值得记的干货：直接编辑对应 spec markdown 文件，语言保持简炼；
   - 没有干货：在任务总结中说明“本次改动无新增规范”，直接进入提交环节。

## 硬性卡点

1. **不写假大空废话**：规范必须是具体的编码约定或避坑说明，严禁写口号。
2. **切忌为了更新而更新**：常规改动大多不需要改 spec，没有新认知就直接判定为“无需更新”，严禁无病呻吟。
