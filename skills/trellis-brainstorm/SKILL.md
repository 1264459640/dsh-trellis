# trellis-brainstorm

在任务规划期（planning）使用本技能：明确需求边界、做技术方案设计、录入执行步骤，**必须获得用户明确批准后才能写代码**。

## 方案设计原则（拒绝过度设计）

1. **不做未来设想**：只解决当前明确提出的问题，不提前堆砌抽象层、通用插件或过度配置。
2. **能简单就不要复杂**：20 行直观代码能搞定的，坚决不新建工厂类、策略模式或多层封装。
3. **把关明确不做（Non-goals）**：明确本次坚决不做哪些扩展，避免范围蔓延。
4. **测试友好**：优先考虑改动是否容易写单测，对现有代码的侵入越小越好。

## 查证与提问规则

- **先查代码再问人**：能通过读代码、搜文件、看配置确认的事实，自己查清楚，严禁拿代码里有的内容反问用户。
- **单轮只问一个关键问题**：若涉及产品偏好、需求分歧或高风险取舍，一轮只提一个问题，并给出推荐选项与权衡说明。
- **不问废话**：不问“我可以看下代码吗”等流程套话，直接执行工程探索。

## 规划流程与产物

| 步骤 | 产物/操作 | 重点内容 |
|------|-----------|----------|
| 1. 记下已知需求 | `prd.md` | 记录目标、确认事实、核心需求、验收标准、明确不做的内容（Non-goals） |
| 2. 技术设计（复杂任务） | `design.md` | 影响模块、关键数据流、对外接口变动、验证命令与回滚预案（小任务可省略） |
| 3. 拆分执行步骤 | `task.json.steps` | 用 `trellis_task_update` 录入步骤，每步写明验收标准与验证方式（ai / human） |
| 4. 汇报总结并等待确认 | 停止输出，等待回复 | 向用户呈现最终方案总结，明确询问是否同意开始编码 |

## 硬性卡点

1. **用户说“直接开干”不等于批准跳过规划**：必须拿出具体方案并经用户确认。
2. **未获批准严禁改动业务代码**：方案汇报后必须停住，只有用户明确回复批准（如“可以”、“OK”、“同意”、“批准”）后，才可用 `trellis_task_update` 将任务状态切为 `in_progress` 并开始编码。
3. **需求或方案有实质变更必须重新确认**。
